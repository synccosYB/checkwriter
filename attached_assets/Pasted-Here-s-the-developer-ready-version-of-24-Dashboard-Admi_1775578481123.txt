#24 — Dashboard & Admin Pages Redesign

Objective

Redesign all dashboard, operational, admin, and utility pages in the Synccos Check Writer app so they fully match the new corporate/professional design system established in the layout overhaul.

This task is about applying the new visual system to the actual product pages users work in every day, while preserving all existing behavior, routing, permissions, and data flow.

What & Why

After the design system and layout shell are upgraded, the next step is to bring the actual pages up to that same standard.

Right now, many pages still feel like a mix of:

default MUI components
inconsistent card styling
uneven spacing
mismatched table styles
older colors and chip states
pages built independently without one clear visual hierarchy

This task should make the app feel like one polished fintech platform from page to page.

The target experience is:

clean
corporate
efficient
financially trustworthy
visually consistent
easy to scan
strong use of whitespace
refined use of tables, cards, filters, and status states

This is not about adding features. It is about making existing workflows look and feel premium.

Dependency

This task depends on completion of:

The page redesign should consume and follow the centralized theme, layout shell, spacing system, component styles, and shared UI primitives created there.

Technical Guidance for Developer
Preserve Functionality
Do not change business logic
Do not change APIs
Do not change route behavior
Do not change permissions
Do not change form submission behavior
Do not change data transformations unless necessary for visual rendering only
Use Theme-Driven Styling

All redesign work should consume:

centralized MUI theme
shared spacing rules
standardized card styles
standardized buttons/inputs/chips
shared layout patterns

Avoid:

one-off hardcoded colors
page-specific ad hoc style systems
inline style sprawl
reintroducing old green/teal tones
visual inconsistency between admin and user pages
Visual Consistency Rule

If two pages solve similar UI problems, they should use the same design pattern.

Examples:

table pages should share one toolbar pattern
status chips should follow one system
settings pages should share one section-card structure
summary metric cards should follow a common pattern
empty/error pages should use one family of layouts
